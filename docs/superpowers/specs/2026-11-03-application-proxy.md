# Windows application proxy

Build an independent Application Proxy workspace. It is off by default and never starts merely because NodeCloak starts. Browser-profile proxy configuration, credentials, routing and cloud sync stay separate.

Users save named proxy destinations, assign them to detected Codex, ChatGPT, Claude or a selected executable, and explicitly start/stop application routing. Reuse supported HTTP/HTTPS/SOCKS5/VLESS/VMess/Hysteria2 connection types and node parsing. Secrets belong to a distinct OS credential-store namespace, not settings, argv or diagnostics. Rules and destinations are local-only in this version.

One owned sing-box TUN process routes matched executable paths to their assigned outbound; unmatched traffic and NodeCloak/browser relay processes go direct. Generate escaped, anchored, case-insensitive path patterns internally because the pinned core's literal path matching is case-sensitive. Never accept user-supplied regular expressions. Match application identity and install paths, not a broad executable-name rule: the installed Codex desktop itself is named ChatGPT.exe. Include known Codex CLI components. Refresh registered package paths at start; do not blanket-match shared WebView/system hosts. Other applications' existing explicit proxies and loopback connections cannot be transparently overridden by TUN; show this limitation in diagnostics.

Windows requests administrator consent only when starting the independent helper. The normal desktop stays unelevated. Parent/helper use a local, ACL-restricted, authenticated named pipe with peer PID checks. The elevated entry accepts a bounded typed request, rebuilds fixed network configuration and executes only its embedded hash-pinned core. Extract the elevated core into a freshly created directory protected for SYSTEM/Administrators, never a user-writable temp executable. No arbitrary config, command, file path or remote control listener is accepted.

The TUN has a unique NodeCloak interface name, IPv4/IPv6 routes, process routing and an authenticated loopback-only connection controller. DNS retains system settings in this first version; do not claim per-application DNS privacy. Detect other active VPN/TUN default-route owners before changing routes. Do not change the system HTTP proxy or global DNS. Explain the temporary routing change before the user starts it.

Runtime readiness requires the owned core, interface and controller, not a coincidentally open port. Stop, startup failure, owner EOF, desktop quit and update preparation must tear down only owned resources. Use a graceful core interruption and bounded fallback; verify interface/routes are released. Do not delete other adapters, routes or services. A failed selected proxy does not fall back to direct. Startup/stop errors remain actionable and redacted; show connection evidence and matched application paths.

Validation uses real sing-box configuration checks, disposable executables/loopback proxy fixtures, administrator-only TUN integration and before/after network state. Verify available real applications without sending chat messages, handling account credentials or force-closing user work. Missing applications or denied OS elevation are recorded as unverified, never represented as successful tests. Existing browser proxy/native checks remain required.
